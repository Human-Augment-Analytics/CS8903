### The Paper's Structure (3 Parts)

1. **The Problem** — why is facilitating cross-disciplinary, cross-faculty collaboration in an online space difficult? What problems occur? (This is the discovery work already done — the audits, the observed failures.)
2. **The Solution** — the researcher guide, formalized and written as a method. Example framing: "we ask each group to send one representative, and then they must do X, then Y..."
3. **The Implementation** — how this gets rolled out in HAAG specifically, starting next semester. This section starts with: "we assessed all projects and identified which groups should be created based on commonalities."

### New Deliverable: The Implementation Doc

This is described as my **next and final markdown file** for this semester. It should NOT be written for researchers (that's what the existing guide is for) — it should be written for **admin** who are creating the unit groups and distributing information at the start of a semester.

**What it needs to cover:**
- How units get created — what parameters determine which projects go into which unit
- Bri's own method so far has been arbitrary — she looked at each project's main focus and grouped by commonality (current units: 3D Vision, UI, Image Processing, R Scripting, Methods Development; NLP was planned but never created)
- **Edge case to address:** projects can shift categories over time (example given: Bird Audio started as an image processing project using object detection, but evolved into a UI-focused tool for biologists). The doc should think through whether/how to handle projects that no longer fit their original unit
- Goal: give explicit parameters so unit assignment doesn't rely purely on admin discretion — more consistency in how it's administered
- Bri flagged this as a **second possible failure point** for past collaboration efforts — not just what happens in meetings, but whether people were grouped well in the first place. This should be evaluated once survey results eventually come in

## Reframing for the Paper — Terminology Matters

Bri raised a significant point: the name "unit meetings" and HAAG-specific terminology limits both the paper's audience and, historically, how the project itself was scoped.

- The paper needs to speak to a **broader audience** — other research groups, program managers — not just HAAG
- Avoid HAAG-specific jargon in the paper. Internally, "unit meetings" is fine to keep using, but the paper should reframe this as a **general collaboration facilitation problem**, not a meeting-logistics problem
- The real narrative: people are collaborating all the time, with wildly different levels of success. Some groups do it well, some don't. This project studied both to learn what separates them, then used those lessons to redesign the system
- I confirmed my understanding: strip HAAG-specific terms so the paper generalizes to any org with similar collaboration challenges

### The Bigger "Why" Behind the Whole Initiative

Bri restated the two core goals this work is meant to serve:
1. **Reduce duplicate work** — if someone has already solved a problem, can others access that knowledge instead of re-solving it?
2. **Increase access to CS expert supervision** — grouping by topic gives researchers more exposure to relevant faculty/advisor expertise
