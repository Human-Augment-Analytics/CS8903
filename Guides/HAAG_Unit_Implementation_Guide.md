# Unit Formation & Assignment Guide
## For HAAG Admin

---

## 1. Purpose of This Doc

This doc is for HAAG admin who create unit groups and assign projects to them, typically at the start of each semester. It explains how units come to exist and how projects get sorted into them.

This is different from the **Unit Researcher Guide**, which assumes units already exist and explains how researchers participate in them once assigned. This doc covers the step before that — how the units themselves get formed.

## 3. How Units Get Formed

A unit should be created around a shared **technical method or research area**, not a shared application domain. Two projects can look similar on the surface (e.g., both involve images) while actually requiring very different technical approaches, or look unrelated on the surface while sharing a core method.

Before forming a new unit, consider:

- **Is there enough volume to justify it?** A unit should have enough projects to support a standalone bi-weekly meeting. A single project does not need its own unit — it can be folded into an existing one or grouped informally until more projects with similar focus appear.
- **Is there a lead available?** A unit needs either a faculty advisor or a computational advisor willing to lead it. If neither is available yet, the unit can still be created and run without one temporarily, with the intention of advertising it to recruit a lead later. Meetings should still happen even without a lead present.

---

## 4. How to Assign a Project to a Unit

Use the following checklist when placing a project into a unit. This is intentionally lightweight — a guide for judgment, not a rigid formula.

1. **What is the project's core technical method?** Focus on the method (e.g., object detection, natural language processing, UI/UX design), not the subject-matter domain (e.g., biology, healthcare, finance).
2. **Does that method match an existing unit's focus?** If yes, assign the project there.
3. **If it fits more than one unit,** consider which unit has more capacity, or more relevant faculty/advisor expertise for that project's specific needs.
4. **If it fits no existing unit,** revisit Section 3 to evaluate whether a new unit should be created.

This process currently relies on admin judgment applied consistently through this checklist, rather than a strict formula. It is meant to reduce inconsistency compared to fully ad hoc placement, not eliminate subjectivity entirely.

---

## 5. Known Limitation — Projects That Shift Over Time

A project's core technical work can evolve past its original unit's scope over the course of a semester or across semesters.

**Example:** The Bird Audio project began as an image-processing project, using object detection techniques to identify patterns in audio-derived visual data. Over time, it evolved into a UI-focused tool built for biologists to use directly, shifting its core focus from image processing to UI/UX.

This is a known, unresolved limitation. This doc does not propose a formal reassignment policy at this time. Admin should be aware that a project placed correctly at the start of a semester may no longer fit its unit by the end of it, and use judgment accordingly. This is flagged here as a candidate for future refinement, ideally once more data is available on whether unit placement affects collaboration outcomes.

---

## 6. Dissolving a Unit

A unit should be considered for dissolution when:

- It has lost most of its original member projects (e.g., due to project completion or reassignment) and does not have enough remaining projects to justify continuing as a standalone unit
- It has gone a full semester without functioning meetings or an active lead, with no plan in place to recruit one

Both R Scripting and 3D Vision reached this point in a prior semester. In both cases, membership dropped significantly and consistent meetings did not continue. When a unit reaches this state, admin should:

1. Reassign any remaining active projects to the closest-fitting existing unit using the checklist in Section 4
2. Archive the unit's Slack channel and any associated materials rather than deleting them, in case the unit needs to be reconstituted later
3. Document the reason for dissolution briefly, for institutional memory
